# 02.8 Approve or decline rejoin requests

Feature: 02 Trips
Depends on: 02.1, 02.3, 02.4, 02.7

Goal: the creator sees members' pending rejoin requests (02.7) and approves or declines them; approving moves the member's login to the new phone.

Behavior
- **Who decides** (ISSUE-047): the creator, for every other member's request. Nobody decides a request for themselves. The creator's own request is decided by their backup alone (02.10); with no backup, nobody can decide it until 02.11 (any other member, after a waiting period) (ISSUE-056). Ended trips work the same.
- `GET /api/trips/{trip_id}/rejoin-requests` (`trip_member`, 02.4) answers `200` with `{"requests": [{"id", "status", "created_at", "member": {…}}, …]}`: the `pending` requests the caller may decide, oldest first. The first three fields are 02.7's request object; `member` is 02.3's object for the member asked for.
- `POST /api/trips/{trip_id}/rejoin-requests/{request_id}/approve` (or `…/decline`), no body, answers `200` with `{"request": {…}}`: 02.7's object, now `approved` or `declined`.
  - **Approve**, in one transaction: the request becomes `approved` with `closed_at`, and its `token_hash` becomes the member's. From then on the new phone's token works and the old one gets `401 token_invalid` (02.4). The member's ID, name, role and `joined_at` stay the same.
  - **Decline**: the request becomes `declined` with `closed_at`. Its token never works; the member's current login is untouched.
  - Only a `pending` request can be decided, so if two people decide at once, the first wins.
- Errors, besides 02.4's: no such request in this trip → `404 request_not_found`; a request the caller may not decide → `403 not_allowed`; a request that's no longer `pending` → `409 request_closed`.

Acceptance
- [x] Yusuf asks to rejoin: the creator's list shows his request with his member object; Yusuf's old phone and another friend get an empty list.
- [x] The creator approves → `200`, `approved`; the new token loads the trip (02.6) as Yusuf with the same member ID; the old token gets `401 token_invalid`; the creator's list is empty again.
- [x] Declining instead → `declined`; the request's token still gets `401` and the old one still works.
- [x] A friend or Yusuf's old phone deciding Yusuf's request → `403 not_allowed`. With no backup, the creator's own request is in nobody's list, and anyone deciding it → `403 not_allowed` (with a backup, see 02.10).
- [x] Deciding a request a second time, or deciding a `replaced` one → `409 request_closed`; a made-up request ID or one from another trip → `404 request_not_found`.
- [x] If someone else decides the request between the check and the save, the answer is still `409 request_closed` and the member's login doesn't change.
- [x] Listing and deciding work the same in an ended trip.

Out of scope: the creator's own request (02.10, 02.11), the requester checking their request (02.9), the app screens (05.4–05.6), telling anyone a request is waiting (no notifications yet).
Later: a member's own old phone approves a request for themselves (a phone upgrade, not a loss) or cancels one that isn't theirs, not only the creator's (02.11); record who decided each request.
