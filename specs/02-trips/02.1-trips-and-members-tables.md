# 02.1 Trips and members tables

Feature: 02 Trips
Depends on: 01.3, 01.4

Goal: the database tables for trips and the people in them, with the rules the rest of the app relies on enforced by the database itself.

Behavior
- One migration, `0001_trips_and_members.sql`, creates both tables. IDs and times are `TEXT` in the 01.4 formats.
- `trips`: `id`, `name`, `join_code` (unique; its format comes from 02.2), `status`, `created_at`, `ended_at`.
  - `status` is `active` (open for posting, parts can be wrapped up) or `ended` (End trip done, 09.3). Nothing else.
  - `ended_at` is set if and only if `status` is `ended`.
- `members`: `id`, `trip_id` (must point to a real trip), `display_name`, `name_key`, `role`, `token_hash` (unique), `joined_at`.
  - `role` is `creator` or `member`. A trip can never have two creators.
  - `display_name` is unique within a trip, ignoring case **in any language**. The database enforces this on `name_key`, made by `name_key()`: Unicode-normalized, case-folded, extra spaces removed (ISSUE-046, ISSUE-049).
  - Only a **hash** of each member's token is stored, never the token itself, so a copied database can't be used to log in. Token creation and checking come in 02.3–02.5.
- No columns for destination, route or country: trips can be anywhere (CLAUDE.md). No member colors either; 06.3 derives them in the app.

Acceptance
- [x] App startup applies `0001_trips_and_members.sql`; a restart doesn't re-run it.
- [x] Invalid `status` or `role` values are rejected by the database.
- [x] A second creator in the same trip is rejected.
- [x] Duplicate `join_code`s and duplicate `token_hash`es are rejected.
- [x] A member pointing to a missing trip is rejected.
- [x] `ended_at` without `status = ended` (or the reverse) is rejected.
- [x] Two members of one trip can't share a name: "Asha" vs "asha", "Zoë" vs "ZOË", "Asha" vs " Asha  ". The same name in different trips is fine.

Out of scope: endpoints (02.3+), join-code format (02.2), token creation/checking (02.3–02.5), parts (09.1), name length limits (decided in 02.3/02.5).
Later: none

Consistency check (vs. all specs + CLAUDE.md)
- Checked against: CLAUDE.md (destination-agnostic; Rules: endpoints follow 01.4), product decisions (creator-only actions ISSUE-003; parts ISSUE-033), 01.3, 01.4, 02.2–02.6, 04.3, 06.3, 09.1–09.7, 12.1.
- Findings:
  - ISSUE-046 (decision): can two members of one trip share a name? Names appear in the timeline and in the story, so duplicates would be ambiguous.
  - ISSUE-047 (gap): no spec covers a member who loses their phone or reinstalls the app. Their token (04.3) is gone, and rejoining (02.5) would create a *second* member, splitting their posts in the story. Decided: creator-approved rejoin (new specs 02.7–02.9, 05.4–05.5). The table needs no change: approval just replaces `token_hash`.
  - ISSUE-049 (found while building): SQLite's case-insensitive matching only covers A–Z, so `name_key` was added.
- No clash:
  - The first migration name matches 01.3's example.
  - `TEXT` IDs and times match 01.4.
  - The creator role matches ISSUE-003.
  - `active`/`ended` fit parts: wrapping a part doesn't change trip status (09.2), End trip sets `ended` + `ended_at` (09.3).
  - Story-job states live in jobs (12.1), not in trip status.
