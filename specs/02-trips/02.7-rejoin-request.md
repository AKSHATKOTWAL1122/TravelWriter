# 02.7 Rejoin request

Feature: 02 Trips
Depends on: 02.1, 02.2, 02.3, 02.4, 02.5

Goal: a member on a new phone ("I'm already in this trip") asks to get back in as themselves, and gets a login that starts working once someone approves (02.8).

Behavior
- `POST /api/trips/rejoin` with `{"join_code": "…", "display_name": "…"}`, no token needed. Answers `201` with `{"request": {"id", "status", "created_at"}, "trip": {…}, "member": {…}, "token": "…"}`. `trip` and `member` are 02.3's objects (`member` is the existing member); `status` is `pending`.
- The code is read as in 02.5: unknown or impossible → `404 trip_not_found`. The name follows 02.3's `MemberName` (else `422 validation_error`) and is matched by `name_key` (02.1), so "yusuf " finds "Yusuf". Nobody in the trip with that name → `404 member_not_found`, with a message suggesting joining as someone new.
- Any member can be asked for, the creator included, also in an ended trip (logins outlive the trip, 02.4).
- **Login** (ISSUE-055): `token` comes from `new_token()` (02.3); only its hash is stored, on the request. It opens nothing (`401 token_invalid`, 02.4) until approval (02.8) puts it on the member. The member's current login keeps working until then.
- **Asking again** for the same member replaces their pending request: it becomes `replaced` and its token never works (ISSUE-054). Done in one transaction; the database allows at most one pending request per member.
- New table `rejoin_requests` (migration `0002_rejoin_requests.sql`): `id`, `member_id`, `token_hash` (unique), `status` (`pending`, `approved`, `declined` or `replaced`), `created_at`, `closed_at` (set if and only if the request is no longer `pending`). Requests don't expire.

Acceptance
- [x] Asking with the code typed loosely and "yusuf " for "Yusuf" → `201` in the shape above, `pending`; the database has only the token's hash; the token gets `401 token_invalid` and Yusuf's old token still works.
- [x] An unknown code → `404 trip_not_found`; a name nobody in the trip has → `404 member_not_found`; "Yusuf 2" → `422 validation_error`.
- [x] Asking again for Yusuf leaves one `pending` request; the first is `replaced` with `closed_at` set. Requests for two different members can both be pending.
- [x] Asking for the creator works, and so does asking in an ended trip.
- [x] The database rejects a second `pending` request for one member, an unknown `status`, and a `closed_at` that doesn't match the status.

Out of scope: approving or declining (02.8), checking the request (02.9), the app screens (05.4, 05.5), limiting wrong attempts (ISSUE-051).
Later: none
