# 02.10 Backup approver

Feature: 02 Trips
Depends on: 01.3, 01.4, 02.1, 02.4, 02.6, 02.7, 02.8

Goal: the creator picks one other member as their backup, who alone approves or declines the creator's own rejoin request (02.7), taking effect at once (ISSUE-056).

Behavior
- `PUT /api/trips/{trip_id}/backup` (`trip_member`, 02.4) with `{"backup_member_id": "…"}` picks that member, replacing any earlier backup; `{"backup_member_id": null}` leaves the trip with none. Answers `200` with `{"backup_member_id": …}`, the ID or `null`. Only the creator can call it, at any time, also in an ended trip. A new trip has no backup.
- 02.6's answer gains the same `backup_member_id`, so every member sees who the backup is (extends 02.6).
- **The creator's request** (extends 02.8) is decided by the backup alone, exactly as the creator decides a member's: approving moves the login at once and the old one stops working. It's in the backup's list and nobody else's. With no backup, nobody can decide it yet (02.11).
  - Whoever is the backup at the moment of deciding counts, also for a request made before they were picked.
  - Members' requests stay with the creator; the backup gets no other powers.
  - 02.8's `403 not_allowed` message for the creator's request says who can decide it: the backup, or nobody yet.
- The backup stays the same member after any rejoin, the creator's or the backup's own (member IDs never change, 02.8).
- New column `members.is_backup` (migration `0003_backup.sql`): the database allows at most one backup per trip, and never the creator.
- Errors, besides 02.4's: a caller who isn't the creator → `403 creator_only` (new; 09.2, 09.3 and 09.6 reuse it); an ID that isn't a member of this trip → `404 member_not_found` (02.7); the creator's own ID, or no `backup_member_id` field → `422 validation_error`.

Acceptance
- [x] Mei creates a trip; Kofi and Lucía join: 02.6 shows `backup_member_id` `null` to all three. Mei picks Kofi → `200`, and all three see Kofi's ID. Picking Lucía moves it to her; `null` clears it.
- [x] With Kofi as backup, Mei asks to rejoin: the request is in Kofi's list only. Kofi approves → the new token loads the trip as Mei (same ID, still creator), her old token gets `401 token_invalid`, and Kofi is still the backup. Declining instead keeps her old login.
- [x] Mei's old phone or Lucía deciding Mei's request → `403 not_allowed`. If Mei moves the backup to Lucía first, Lucía can decide it and Kofi gets `403 not_allowed`. With no backup it's in nobody's list (as in 02.8).
- [x] Kofi sees none of the members' requests and deciding Lucía's → `403 not_allowed`; Mei still decides it.
- [x] Kofi or Lucía picking a backup → `403 creator_only`; Mei picking herself or sending no field → `422 validation_error`; a made-up ID or another trip's member → `404 member_not_found`. The backup is unchanged after each.
- [x] Picking works the same in an ended trip. The database rejects a second backup in one trip and a creator as backup.

Out of scope: the creator's request with no backup (02.11), the app screens (05.5, 05.6), telling the picked member (no notifications yet).
Later: the picked member agrees first, or steps down; record who decided each request (02.8's Later).
